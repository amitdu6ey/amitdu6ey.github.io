Consumer-driven contract testing with Pact

JPMorgan Chase, 2026 – present

Notification platform, Pact, GraphQL, Java, Spring Boot

The notification platform has several clients, and none of them should have to release in lockstep with it. Consumer-driven contracts make that possible. Each client records exactly which parts of the GraphQL API it relies on, and the platform is verified against every one of those contracts before it ships.

Applies to
Omnichannel notification platform and its clients
Goal
Producers and consumers ship independently
Catches
Breaking API changes, at build time instead of in production

Design

Why contracts instead of more integration tests

End-to-end tests across every client are slow, flaky and need everything deployed together, which is exactly the coupling we wanted to remove. A schema check alone knows what the API offers but not what clients actually use. A consumer-driven contract fills that gap: it is a precise record of the queries each client sends and the fields it depends on, and nothing more.

Making a pact

A consumer's own unit tests run against a Pact mock of the API. Each interaction — the GraphQL query and the shape of the response the client expects — is recorded into a pact file and published to the broker, tagged with the consumer's version and branch. Because the pact comes from the client's own tests, it stays as narrow as the client's real usage.

Verifying the provider

In the platform's build, every relevant consumer pact is replayed against the real API, with provider states setting up the data each interaction assumes. The results go back to the broker, which builds a matrix of which provider versions work with which consumer versions.

Gating deploys

Before any release, of the platform or a client, can-i-deploy asks the broker whether the version about to ship is compatible with everything already running in that environment. If any pact fails, the release is blocked in the pipeline, not discovered by users.

Evolving the API safely

Renaming a field is the classic break: the provider's tests pass, and every client that reads the old name fails. With contracts, that change fails verification immediately. The safe sequence is additive: add the new field alongside the old one, ship, let clients move over, and remove the old field only when no pact references it any more.
