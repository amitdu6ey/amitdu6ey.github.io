Design

Precompute membership, don't evaluate it per request

An audience is a rule over user attributes. Evaluating rules at request time makes every flag check as slow as its most complex audience, and it gets slower as audiences grow. The platform instead keeps membership materialised: when an attribute or a rule changes, an event goes onto Kafka and compute jobs recalculate only the memberships that change. The request path is left with one cheap question, answered by key.

Write path: at-least-once, idempotent by design

Events are keyed so that every change for the same user lands on the same partition, which keeps per-user ordering. Workers write the membership first and commit the offset second. A crash between the two replays the event, so every write is an upsert of the final state rather than an increment. Replays then change nothing, and the pipeline never needs exactly-once machinery to be correct.

Heterogeneous load on one common compute

The same fleet handles two very different shapes of work. One is a steady stream of small incremental updates: one user changes and a handful of memberships move. The other is bulk recompute: a new or edited audience can touch millions of rows at once. Running both on one common compute keeps utilisation high and the system simple, but bulk work must not starve the incremental stream. Bulk recomputes are broken into bounded, idempotent units, and the latency-sensitive stream gets its own lane so it never queues behind a backfill. Membership store on CockroachDB

Memberships need strong consistency, a flag must not flip back and forth between reads, and they need to scale horizontally past 100M rows. CockroachDB splits the table into ranges and replicates each one with Raft, so a node can fail without losing writes or taking reads offline. Keys are chosen so that "which audiences is this user in?" is a point read on one range, and so that a big recompute spreads its writes rather than hammering one hot range. Tail latency

p99.99 went from 3 seconds to 300 milliseconds. At that percentile the problem is never the average request; it is the rare slow path that one request in ten thousand hits. The things that create those paths in a system like this are:

  • Work that grows with data. Any request-time evaluation or fan-out that scales with the number of audiences.
  • Hot keys and hot ranges. One popular key or a sequential key pattern concentrates load on a single replica set.
  • Contention and retries. Large write transactions overlapping with reads cause conflicts and retries, which surface only in the far tail.
  • Unbounded responses. Payloads that grow with the number of memberships a user holds.

Keeping the read path to a bounded point lookup, and keeping heavy writes small and spread out, is what keeps the tail close to the median.
