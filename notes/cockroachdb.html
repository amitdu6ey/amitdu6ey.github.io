Design

Ranges

A table and its indexes are stored as one sorted key-value space, split into contiguous ranges. Ranges split as they grow and are rebalanced across nodes automatically, which is how a table scales past any single machine. The practical consequence is that where a key sorts decides which range, and therefore which nodes, serve it.

Raft per range

Every range is replicated, three ways by default, and each range runs its own Raft consensus group. A write is committed once a majority of the range's replicas have appended it to their log, so with three replicas any single node can fail without losing committed data or availability. One replica holds the range lease: it serves consistent reads locally and proposes writes for that range.

Serializable transactions and retries

Transactions run at serializable isolation by default. When two transactions conflict, one of them is asked to retry, with error code 40001, rather than silently reading stale data. Clients must therefore wrap transactions in retry logic, and keeping transactions small and short is the main lever against contention. In a read-heavy system the important rule is that bulk writes should never share a transaction, or hot keys, with the latency-sensitive read path.

Key design and hot ranges

Because ranges are sorted by key, sequential keys such as auto-increment IDs or timestamps send every new insert to the last range, which makes it a hotspot. Random UUIDs or hash-sharded indexes spread writes across ranges instead. The rule of thumb: choose primary keys so that the hottest read is a point lookup on one range, and the heaviest write pattern is spread across many.

Moving from MariaDB

The migration I worked on changes more than the connection string. Auto-increment primary keys become a hotspot risk and are better replaced. Transactions need retry handling that MariaDB code never had. The SQL dialect is PostgreSQL-compatible rather than MySQL-compatible, so queries and types need review. With schema changes versioned in Flyway and releases done blue-green, the cut-over could happen without downtime.
