Elasticsearch capacity planning

Applies to the employee search service

Elasticsearch

Capacity planning for search starts from a question people often skip: is this a data problem or a traffic problem? A directory of the firm's people is small by search standards. With more than 80 systems calling it, though, the constraint is concurrent queries and tail latency, not storage. That changes the whole shape of the cluster.

Data
One document per person, on the order of the firm's 350K+ employees
Traffic
80+ downstream systems, interactive lookups
Constraint
Query concurrency and tail latency, not storage

Design

1. Estimate data volume

Documents × average document size, then add room for index structures and multiply by the number of copies. For a people directory the answer is small. For example, half a million documents at a couple of kilobytes each comes to around a gigabyte per copy, which settles the storage question quickly. It also hints at where the real work is.

2. Size shards to the data, not the node count

Every search fans out to one copy of every shard, so extra shards add work to every query without adding capacity. Elastic's own guidance is to aim for shards in the tens of gigabytes. A directory index is far below that, so one primary shard is the natural choice. More primaries would only make each query more expensive.

3. Add read capacity with replicas

Any copy of a shard can serve a search, so replicas are how read throughput scales. With a replica on every data node, every node can answer every query locally, load spreads evenly, and losing a node costs capacity rather than availability. Indexing pays for each extra copy, which is cheap for a slowly changing directory.

4. Size for concurrency and the tail

Each search holds a search thread for as long as it runs, so a node's throughput is roughly its search threads divided by query latency. Size the cluster so that the expected peak query rate from all callers uses only a fraction of that, leaving headroom for bursts. When search thread pools fill, queries queue and then get rejected, and the tail shows that first.

5. Memory

Give the JVM heap no more than about half of the node's RAM, and keep it below the threshold where compressed object pointers stop working, around 32 GB. The rest belongs to the operating system's page cache. For a small index, the whole thing then lives in memory and searches never wait on disk.

6. Prove it with a benchmark

Estimates set a starting point; a benchmark with the real query mix sets the answer. Elastic's Rally replays representative queries at increasing rates. The numbers to watch are p99 latency, search thread pool rejections, garbage-collection pauses and cache hit rates. Capacity is the highest rate where all four stay healthy, minus headroom.
