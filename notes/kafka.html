Kafka: partitions and mixed load on one common compute

Applies to the A/B testing platform

Kafka, Java, Spring Boot

The membership platform runs two very different workloads on the same compute: a live stream of small updates and occasional bulk recomputes that touch millions of rows. Kafka partitions are what make that safe, provided the partitioning, the lanes and the backpressure are designed together.

Load
10M+ membership updates a day
Workloads
Small incremental updates and large bulk recomputes
Compute
One shared consumer fleet for both

Design

Partitions are the unit of ordering and parallelism

Kafka only orders messages within a partition, and inside a consumer group each partition is read by exactly one consumer at a time. So the partition count is the ceiling on parallelism, and the message key decides what stays in order. Keying membership events by user keeps every change for one user in sequence and spreads users evenly across partitions. The thing to watch is skew: a single very hot key, or a key with low cardinality, turns one partition into the bottleneck no matter how many workers exist.

Choosing a partition count

The count has to cover peak throughput divided by what one consumer can sustain, plus headroom for catching up after an outage. It is worth getting roughly right up front: adding partitions later changes which partition a key hashes to, which breaks per-key ordering across the change. Too many partitions has a cost too, in rebalance time and per-partition overhead, so the target is enough for peak and catch-up, not as many as possible.

Two lanes on one fleet

Small live updates and bulk recomputes have opposite needs: one wants low latency, the other wants throughput. Putting them in separate topics lets the same consumers treat them differently without separate fleets. Bulk work is published as many bounded chunks, each small enough to finish quickly, safe to retry and restartable on its own, rather than as one giant job. Workers serve the live lane first and use the consumer's pause and resume on bulk partitions as a throttle: when live lag rises, bulk stops pulling; when it falls, bulk fills the spare capacity.

Backpressure, scaling and rebalances

Consumer lag per partition is the signal for everything: for the throttle above, for alerting, and for scaling the fleet out, which helps only up to the partition count. Capping records in flight per partition keeps each poll loop short, so a worker never misses its heartbeat on a slow batch and triggers an unnecessary rebalance. When the group does rebalance, incremental cooperative assignment moves only the partitions that need to move, instead of stopping every consumer.

Failure handling

Offsets are committed after the write, so delivery is at-least-once and every write is an idempotent upsert of final state; a replay changes nothing. A message that keeps failing is retried with backoff and then parked on a dead-letter topic, so one bad record cannot block its partition.
